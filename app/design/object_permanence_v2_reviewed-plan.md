# Object Permanence v2 - Implementation Plan

Source design: `app/design/object_permanence_v2_reviewed.md` (Status: draft, two open questions, both carried below as phase blockers)
Conventions read: `CLAUDE.md` (repo root, git workflow), `app/docs/CONVENTIONS.md` (authoritative for the app code: seam rule, render discipline, trust rules, prose rules, Commands), `app/docs/CURRENTNESS_AUDIT.md`, `app/docs/RUNTIME_VERIFICATION_QUEUE.md`, `app/design/object_permanence_v1_reviewed-plan.md` (structure and the as-built-amendment convention). Frozen contracts read in full: `docs/STATE-SCHEMA.md`, `docs/SCRIPT-VOCABULARY.md`. Spot-checked on disk: `plugins/claudhd/scripts/state.js`, `vocab.js`, `quick.js`, `root.js`, `app/src/core/**`, `app/src-tauri/src/lib.rs`, `app/test/**`, both `package.json` files, `~/.claude/plugins/cache/claudhd/claudhd/` (installed versions 1.0.0, 1.0.1, 1.0.2, 1.0.3, 1.0.5 - not contiguous, which the version resolver must survive).

Verification command(s):

- **Plugin suite (repo root):** `npm test` -> `node --test "test/*.test.js"`. Zero dependencies, node's own runner. This is the gate for phase 1 and for any later phase that touches `plugins/`.
- **App suite (`app/`):** `npm test` -> `vitest run`, and `npm run typecheck` -> `tsc --noEmit`. These two are the reviewer gate on every app phase (phases 2 through 7). From the repo root the app suite is also reachable as `npm run test:app`.
- **App runtime:** `npm run acceptance` (live fleet scan, `tsx scripts/acceptance.ts`), `npm run tauri:dev` (app smoke), `npm run tauri:build` (NSIS bundle, only if the release bundle is re-cut).
- **Release (operator step, between phase 1 and phase 3):** `npm run release -- patch` at the repo root, then `claude plugin update`. See cross-cutting concern 1.

Which suite gates which phase: phase 1 is plugin work and is gated by the root `npm test` only. Phases 2 through 7 are app work and are gated by `app`'s `npm test` plus `npm run typecheck`, plus the named runtime check in that phase. No app phase may leave the root suite red, and phase 1 may not change any app file.

As-built amendment convention (carried from the v1 plan): when a phase lands, the implementer appends a `**As-built amendments (phase-N review):**` line to that phase recording every divergence from this plan, and the relay moves that phase's `**Status:**`. The source design doc is never edited by the implementer; a design-level change is a blocker, not an amendment.

## Summary

Seven phases bring the desktop app onto ClauDHD 1.0's two frozen contracts and add the two surfaces section 10 promised. Phase 1 is plugin-side: `readStateResult()` plus a `state.js read --json` subcommand, with `readState()`'s behavior frozen. Phase 2 opens the single integration seam (the `ScriptRunner` port, the `plugin_run` courier command, the core selection rule and the capability probe) and proves it by moving capture off `idea_append` onto `vocab.js append-capture`. Phase 3 rebuilds the read layer on the six-status result, the build sentinel, and the re-keyed flag set. Phase 4 adds the next-up panel and the pipeline group toggle. Phase 5 wires dispatch. Phases 6 and 7 add the write taps in the design's own order: triage taps, then structural edits.

## Blockers / Open Questions

Nothing blocks phase 1. Two blockers remain, each pinned to the one phase it gates.

One terminal run answers it: `claude "/claudhd:version"` at any ClauDHD project, observing whether the session opens with that command already run or opens idle. If it does not submit, the `copy + open` branch ships and `clipboard_write` enters the courier's scope for that phase. Record the answer in the queue file before phase 5 starts.

**B4 (gates phase 7). The one-line amendment to section 10 of `design/claudhd-1.0-design_reviewed.md`.**

Design section 3 and open question 2 substitute move-up, move-down, and park buttons, and say the narrowing needs an explicit one-line amendment that is the user's to make or refuse. If refused, drag is implemented as ratified and phase 7's UI half changes shape; the verb, its arguments, and the parser in that phase are unaffected either way. Phase 7 does not start until this is answered.

**Resolved in the design, kept here so the numbering stays stable across revisions.**

- **B1 (was phase 2): where the plugin version-selection rule lives.** Resolved in design section 3 ("Plugin discovery: the rule is core, the listing is the courier"). The courier lists version directory names and reports which of the three scripts exist under each; `app/src/core/plugin.ts` holds the pure selection rule and is unit-tested against fixture listings. `app/docs/CONVENTIONS.md`'s "all logic lives in TypeScript" stands, and no `cargo test` gate is added. Phase 2 is the first phase that writes a tap record (capture, `append-capture`), so it owns adding the discriminant and tightening transition validation; phases 5, 6, and 7 add their own verbs and the dispatch discriminant behind it.

## Cross-cutting concerns

1. **Plugin release and install ordering (phase 1 to phase 3).** The app resolves scripts from `<user-home>/.claude/plugins/cache/claudhd/claudhd/<version>/scripts/`, not from this repo's working tree, so phase 1's subcommand is invisible to the app until a release is cut and installed: `npm run release -- patch` at the repo root (bumps `plugin.json` and `.claude-plugin/marketplace.json` together, runs the root suite and the manifest invariants first, commits, pushes, tags), then `claude plugin update`. This must happen after phase 1 lands and before phase 3 starts. Because phase 2's probe is a capability check rather than a file check, an unreleased state of the world is honest rather than silent: every installed version fails the probe, and the provenance line names the newest installed version and says it lacks the read endpoint. That makes the failure path free to verify during phase 2 and makes "the plugin is stale" an upgrade instruction instead of a fleet-wide raw fallback. Rollback: the app degrades to the lenient NOW.md card, and reverting the app is independent of the plugin release.

2. **Frozen contract `docs/STATE-SCHEMA.md` and `readState()` (phase 1).** `readState()`'s null-or-state contract and its six-field normalization are consumed by `checkpoint.js`, `reconcile.js`, `issueRoadmapIds()`, `sentinel-core.js`, and the guards through `modes.js`. `readStateResult()` is additive and sits alongside it; changing `readState()`'s return shape breaks every one of those callers. The doc extension ships in the same commit as the code, and the untouched, still-green `test/state.test.js` and `test/state-v2.test.js` are the evidence that the frozen half did not move. Rollback: remove the new export and the CLI block; nothing else depends on it until phase 2's probe.

3. **New mutation port and the seam rule (phase 2, ripples to phases 6 and 7).** `ScriptRunner` is the first port that can change a file outside the app data directory. `app/docs/CONVENTIONS.md`'s seam rule must record the distinction in the same phase that adds the port: `AppStore` stays the only direct filesystem write port and stays inside `%APPDATA%\claudhd`; `ScriptRunner` invokes a closed set of three script basenames with `cwd` validated against discovered project roots and no caller-supplied path. Every existing import and platform boundary in the seam rule stands, and a core module importing an adapter or a platform API is still a review FAIL. The same phase keeps the "all logic lives in TypeScript" line true by putting the selection rule in `src/core/plugin.ts` and leaving the courier with listing and spawning only. Rollback: the port is inert without a caller; removing the callers disables writes without touching the read path.

4. **Courier public surface: `idea_append` removed, `plugin_run` added, `clipboard_write` conditional (phases 2 and 5).** `idea_append` is the app's one legacy direct project write and the capture window is its only caller, so its removal and the capture rewiring must land in the same phase or capture breaks. `clipboard_write` enters the courier only if active check 3 selects the copy-plus-open branch (B2). Migration: none, no stored data involved. Rollback: reverting phase 2 restores both the command and the duplicate line format, which is the defect being fixed, so prefer forward fixes.

5. **`config.json` schema change (phase 3).** Adds `staleSentinelHours: 6`; removes `stateJsonMaxLagDays`, `cursorBloatWarn`, `cursorBloatCrit`, `cursorStaleWarnDays`, `cursorStaleCritDays`, and `unwrappedMinHours` from the typed defaults. The merge is additive and tolerant, so a stored file still carrying the removed keys must merge cleanly with them ignored, and `app/test/config.test.ts` currently asserts on `cursorBloatWarn` and must be re-cut in the same phase. Ordering: phase 3, in the same commit as the flag re-key, because `npm run typecheck` is a per-phase gate and the two cannot be split without a red tree. Rollback: delete `%APPDATA%\claudhd\config.json` and defaults regenerate.

6. **`FlagId` union change and the fire-rate history (phase 3).** Retiring `cursor-bloat`, `cursor-stale`, and the unwrapped rule and adding `recorded-override` changes a type consumed by `flags.ts`, `model.ts`, `diff.ts`, `history.ts`, and their suites. `history.jsonl` already holds transitions recorded under the retired ids, so the history reader must tolerate an unknown flag id in an old line rather than dropping or throwing on it; the week-two tuning pass (`r-0727-3`) argues from those lines. `app/test/oracle/assassinrpg.expected.ts` names cursor-bloat crit as its non-negotiable anchor and is listed for re-cutting in the design's contracts-touched table; it must be re-cut in this phase, along with the fixtures in `diff.test.ts` and `history.test.ts` that use retired ids. Rollback: none needed, the log is append-only and forward-readable.

7. **`history.jsonl` becomes a three-discriminant union (phase 2, extended in 5, 6, and 7).** Phase 2 owns the split, because capture is the first tap: transition validation narrows to `raised`, `cleared`, and `severity`, and the tap record `{ kind: "tap", atMs, project, verb, outcome }` lands with its first writer. Phase 5 adds the dispatch record and the since-last-open merge on `savedAtMs`. Phases 6 and 7 add their verbs to the closed set. Old lines carry no `kind` discriminator and must keep parsing as transitions; fire-rate code receives transitions only, in every phase. The kill criteria also need two new line types in the existing `r-0727-2` trial log for the read and trust halves; the trial log is not a code artifact and starts no parallel trial. Rollback: dispatch and tap lines are inert to every existing reader once the union lands.

8. **Legacy `.gantry/active-phase.json` (phase 3).** The plugin imports that file into `build` once and then deletes it, and an outside reader racing that migration gets it wrong, so the app stops reading it entirely in the same phase the sentinel model lands. Do not leave a fallback read: a partial migration is exactly the race the removal exists to avoid. Rollback: none; the file is gone on migrated projects.

9. **Prose, vocabulary, and trust rules (every phase that emits copy: 2 through 7).** No em-dashes, no "not X but Y", no three-beat lists, no tagline closers, no emoji, lowercase-friendly and terse. Zero new coined terms. Remedies shown to the user are ClauDHD or Gantry commands, never in-app buttons, with the ratified triage and structural taps as the one exception section 10 carved out. Parse failure returns a raw-fallback result and never a throw or a stale parse shown as current; every displayed number carries its evidence; plugin, launcher, dispatch, and hotkey failures are reported and never swallowed. These are review items on each phase, not polish.

10. **Git workflow and packaging.** Solo repo, linear history, commit straight to `main`, no branches and no PRs (repo `CLAUDE.md`), lowercase `area: what changed` subjects. Phase 1 additionally rides the release loop in concern 1, which pushes and tags. No NSIS rebuild is required by this design; if the installed binary is refreshed after phase 7, `npm run tauri:build` in `app/` produces the per-user bundle, and runtime queue items 1 and 2 (resume templates, installer first run) are still open against it.
